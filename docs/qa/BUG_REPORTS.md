## BUG-01: Malformed JSON returns an HTML error page instead of JSON

- **Severity:** Low | **Priority:** Low | **Related test:** SEC-05
- **Preconditions:** server started with `NODE_ENV` not equal to `production`.
- **Steps:**
  1. `curl -i -X POST http://localhost:3001/api/login -H "Content-Type: application/json" -d "{bad json"`
- **Expected result:** `400` with a short JSON body such as `{"error":"Invalid JSON"}`, consistent with the other API errors.
- **Actual result (predicted from code):** `400` with an HTML page generated by the default Express error handler; in development it contains a stack trace with file paths. `server/index.js` has no error-handling middleware after the routes.
- **Impact:** inconsistent API contract; stack traces expose internals.
- **Suggested fix:** add a final `app.use((err, req, res, next) => ...)` that returns JSON and hides details.

## BUG-02: `POST /api/login` and `/api/register` without a body respond with 500

- **Severity:** Medium | **Priority:** Medium | **Related test:** SEC-06
- **Steps:**
  1. `curl -i -X POST http://localhost:3001/api/login` (no body, no `Content-Type`)
  2. Repeat for `/api/register`, and with `Content-Type: text/plain` and body `hello`.
- **Expected result:** `400`, `{"error":"Email and password are required"}`.
- **Actual result (predicted from code):** `500` with an HTML error page. In Express 5, `req.body` is `undefined` when no parser handled the request, and `const { email, password } = req.body;` in `server/routes/auth.js` runs outside the `try` block and throws a `TypeError`.
- **Impact:** a client error is reported as a server error; noise in logs and monitoring.
- **Suggested fix:** use `const { email, password } = req.body ?? {};`.

## BUG-03: Registered user's quota never resets

- **Severity:** Medium | **Priority:** Medium | **Related tests:** QUO-05, QUO-06
- **Steps:**
  1. Register and log in.
  2. In the database run `UPDATE users SET used = 30 WHERE email = 'qa.user1@gmail.com';`
  3. Send a message in any chat.
- **Expected result:** the requirement must define the policy (for example, a limit per day). A user should not be locked out permanently.
- **Actual result (predicted from code):** `403`, `code: LIMIT_REACHED`, `type: user`. `server/utils/quota.js` only increments `used`; nothing resets it, so the limit of 30 is a lifetime limit.
- **Impact:** after 30 messages the account is useless; the message in the UI suggests registering, which the user has already done.
- **Question for the product owner:** is a lifetime cap intended? If yes, the UI message for `type: user` must say so.

## BUG-04: A new guest row is created for every cookieless request, with no rate limit

- **Severity:** Medium | **Priority:** Medium | **Related tests:** QUO-01, QUO-09
- **Steps:**
  1. Run `SELECT count(*) FROM guests;` and note the value.
  2. Send 100 requests without cookies: `for i in $(seq 100); do curl -s http://localhost:3001/api/quota > /dev/null; done`
  3. Run the count again.
- **Expected result:** guest rows are created only when needed (for example, on the first message) or creation is rate limited.
- **Actual result (predicted from code):** 100 new rows. The `identify` middleware inserts into `guests` for every request without a valid `gid`, and `GET /api/quota` and `GET /api/chats` have no rate limiter.
- **Impact:** database growth by any script; also each new guest receives a fresh quota of 5, so deleting the cookie bypasses the guest limit (already listed as a known limitation).
- **Suggested fix:** rate limit identify-creating routes; create the guest lazily.

## BUG-05: One rate limiter is shared by several routes, so legitimate users get blocked

- **Severity:** Medium | **Priority:** Medium | **Related tests:** RL-01, RL-02
- **Steps:**
  1. Restart the server.
  2. From one IP send 6 successful logins and 4 registration attempts.
  3. Send one more request to either route.
- **Expected result:** each endpoint has its own counter, and successful logins do not consume the budget of failed attempts.
- **Actual result (predicted from code):** `429` on the 11th request. `authLimiter` in `server/routes/auth.js` is one instance used by both `/register` and `/login`, and successful requests are counted. Similarly `messageLimiter` in `server/routes/chats.js` is shared by `POST /api/chats` (create chat) and `POST /api/chats/:id/messages`.
- **Impact:** people on a shared network (university, office) can lock each other out of sign-in.
- **Suggested fix:** separate limiters per route; add `skipSuccessfulRequests: true` for login.

## BUG-06: Guest chats are not available after sign-in or registration

- **Severity:** Medium | **Priority:** Medium | **Related tests:** UI-01, CHT-02
- **Steps:**
  1. As a guest create a chat and send a message.
  2. Register and log in with the same browser.
  3. Open the chat list.
- **Expected result:** either the guest's chats move to the new account, or the UI clearly says they will not be kept.
- **Actual result (predicted from code):** the list is empty. After login `identify` switches the actor from guest to user, and chats are selected by `user_id`; guest chats stay linked to `guest_id`.
- **Impact:** a person who hits the guest limit, registers, and loses the whole conversation.
- **Suggested fix:** on login, move chats with `UPDATE chats SET user_id = $1, guest_id = NULL WHERE guest_id = $2`.

## BUG-07: Rate limiting will apply to all users at once behind a reverse proxy

- **Severity:** High (deployment) | **Priority:** High before release | **Related test:** RL-01
- **Steps (after deployment on Render/Railway, or simulate with `X-Forwarded-For`):**
  1. Open the app from two different devices.
  2. Fail login 10 times from device A.
  3. Try to log in from device B.
- **Expected result:** device B is not affected.
- **Actual result (predicted from code):** both devices share one IP as seen by Express, so device B gets `429`. `server/index.js` does not set `app.set('trust proxy', ...)`.
- **Suggested fix:** configure `trust proxy` for the hosting provider (already in the deployment checklist).

## BUG-08: Valid email domains without MX records are rejected

- **Severity:** Low | **Priority:** Low | **Related test:** REG-10
- **Steps:**
  1. Use a test domain that has only an A record (no MX).
  2. Register `user@that-domain`.
- **Expected result:** per RFC 5321 a domain with an A record can receive mail, so registration is accepted (or the policy is documented).
- **Actual result (predicted from code):** `400`, `Email domain looks invalid`. `domainCanReceiveMail` in `server/routes/auth.js` treats any DNS error or empty MX list as invalid, so a temporary DNS failure also blocks registration.
- **Impact:** rare false rejections of real users.
- **Suggested fix:** fall back to an A/AAAA lookup, and do not block on transient DNS errors.
